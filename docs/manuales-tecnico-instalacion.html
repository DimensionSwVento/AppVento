Manual Técnico — Vento (Plataforma de idoneidad eólica)

Arquitectura, stack, comportamiento, configuración y operación. Audiencia: equipo de desarrollo / on-call. No es el manual de usuario. Fecha: 2026-10-01 · Autor: Mavalan Software

1. Qué es Vento

Plataforma SIG/MCDM que evalúa la idoneidad de zonas para proyectos eólicos en Colombia sobre una malla de hexágonos H3 (resolución 8). El usuario selecciona un área, el sistema agrega un índice de idoneidad (0–100) por dimensión y general, y genera un informe PDF configurable. El admin gestiona variables, datasets, normas, escenarios económicos y usuarios.

  • Modelo: multicriterio (WLC/AHP) en escala 1–5 (−1 = excluida), normalizado a 0–1 con (raw−1)/4. El global y los scores por dimensión vienen precalculados en la máster (parquet); la app no recalcula el modelo: solo agrega y formatea.
  • Dimensiones: Técnica, Ambiental, Social (puntuables) + Económica y Regulatoria (informativas, no puntúan).

2. Arquitectura

Navegador ──HTTPS──▶ Front Next.js (BFF)
                       │  rutas /api/*  (Next route handlers)
                       │    · validan la sesión de Keycloak (Auth.js)
                       │    · reenvían al backend con INTERNAL_API_SECRET + identidad
                       ▼
                   Backend FastAPI (Docker)  ──SQLAlchemy──▶ PostgreSQL
                       │                                        hexagon (1.6M filas), hexagon_meta,
                       │                                        hexagon_variables_pon, catalog_*,
                       └── Keycloak (OIDC/JWT)                   parquet_column, app_config, informe
  • BFF (Backend-for-Frontend): el navegador no habla con el backend directo. Las rutas /api/* del front son route handlers que: (1) exigen sesión válida de Keycloak, (2) reenvían al backend privado (BACKEND_URL) con un secreto compartido (INTERNAL_API_SECRET) y la identidad del usuario (sub + roles). Así el backend puede ser privado en la red.
  • Backend stateless: nada se carga a RAM al arrancar; cada request consulta Postgres en streaming (anti-OOM). Clean architecture: api/ (routers) · application/ (servicios) · domain/ (modelo/consulta) · infrastructure/ (BD, auth, datos).
  • Auth: Auth.js (NextAuth v5) en el front (cookies __Secure-authjs.session-token); Keycloak como IdP (OIDC). El backend verifica el JWT (JWKS de Keycloak) — no emite tokens. Roles admin / analista.

4. Modo TEMPLATE vs BACKEND (clave)

El front opera en uno de dos modos, según NEXT_PUBLIC_USE_BACKEND. Al arrancar se loguea [VENTO] MODO: BACKEND (API real...) o TEMPLATE (demo, sin backend).

NEXT_PUBLIC_USE_BACKEND=false → TEMPLATE =true → BACKEND
Fuente de datos placeholders deterministas (demo, sin API) API real (/api/* → backend → Postgres)
Fallback USE_PLACEHOLDER_FALLBACK = true: todo cae a placeholder false: dato real o VACÍO, nunca cifras falsas
Excluidas SHOW_PLACEHOLDER_EXCLUDED: 6 zonas demo capa real (/tiles/excluded)
Uso demos/QA sin backend producción

Regla de oro: en modo backend el sistema nunca inventa valores. Si una variable no tiene dato (p.ej. no se ingirió), se muestra "—" / vacío. Los placeholders solo existen en modo template. (Backend: real o vacío; nunca placeholder.)

5. Ingesta de datos (comportamiento)

La ingesta es destructiva por dataset (reemplaza todo) y se dispara desde Admin (subir máster / metadatos) o por tool.

5.1 Hexágonos (máster *.h3.parquet)

update_from_parquet → según HEXAGON_INGEST: - copy (por defecto): vía COPY de Postgres. Atómico: TRUNCATE hexagon + COPY en una sola transacción (si el proceso muere a mitad, no deja datos a medias). Streaming dict → tupla → COPY (no materializa el dataset en RAM) → máximo rendimiento. - orm (fallback portable): DELETE + inserción por lotes vía ORM (entornos sin COPY, p.ej. tests). Más lento, no requiere Postgres-COPY. - En la misma transacción se recalcula hexagon_meta (min/max por variable) para la normalización. Los valores del parquet se sanean a tipos JSON nativos (_clean_variables: pandas/numpy → JSON) antes de persistir en hexagon.variables (JSONB). - INGEST_MEM_CAP_MB acota el pico de memoria del proceso de ingesta.

5.2 Catálogo / metadatos (InfoVariables, normas, escenarios, turbinas)

Servicios dedicados, también destructivos por tabla: - metadata_ingest — InfoVariables.xlsx → catalog_variable (label, dimensión, criterio/subcriterio, fuente, licencia, método de cálculo, icon_key, enMapa, pesos). Registra las columnas del documento en parquet_column (nombre ↔ base_code). - catalog_ingest — normas regulatorias → catalog_norma. - economic_ingest — escenarios/series macro → catalog_escenario / economic_*. - bundle_service / master_service — subida del bundle de máster (drag-and-drop en Admin) y estado/versión de la máster (master_version).

5.3 Después de ingerir (obligatorio)

  1. VACUUM ANALYZE hexagon; → mantiene reltuples (usado por warmup) y el visibility map.
  2. Verificar con GET /api/admin/db/overview (solo admin): columnas por tabla + la tríada de códigos de variable en h3 (hexagon_meta) vs catálogo (catalog_variable) vs máster (parquet_column), con el diff de qué falta/sobra.

6. Backend — endpoints

Router /api/tiles/* (datos del mapa) · /api/admin/* (gestión) · /api/historico · /api/health · /api/_debug/*.

Endpoint Qué hace Coste típico
GET /tiles/warmup metadatos + conteo estimado (reltuples, no count(*)) µs
GET /tiles/variables catálogo (meta + catalog_variable) <1 ms
GET /tiles/{z}/{x}/{y} tile del grid (bbox → agregación por zoom, streaming) ms
GET /tiles/detail/{h3} detalle de un hex (PK) 0,1 ms
POST /tiles/area informe: hexes del área (score/dimensiones/variables + ponderadas) ms
POST /tiles/variable · /variables-bulk capa(s) de variable por bbox (bulk = N códigos en 1 scan) el más pesado
GET /tiles/excluded capa completa de excluidos (índice parcial + caché TTL) ms
GET /api/admin/db/overview verificación de ingesta (admin) —
GET /api/_debug/stats · /_debug/inflight RAM/swap/in-flight (gate DEBUG_INFLIGHT=1) diagnóstico

Anti-OOM / concurrencia: - Streaming (stream_results, yield_per) — la RAM no escala con el dataset. - Pool explícito (DB_POOL_SIZE=5 + DB_MAX_OVERFLOW=15 = 20/worker) + cap de threadpool anyio (APP_THREAD_LIMIT=18). Gunicorn 2 workers, --timeout 120. - Trazabilidad: TRACE_REQUESTS, INFLIGHT_WARN, SLOW_REQUEST_MS (logs de saturación).

7. Capacidad (medida con tools/loadtest.py)

Server 2 workers / ~2 GB. Techo útil ≈ 25 usuarios concurrentes explorando. Evidencia: docs/testing/benchmark-carga-h3-2026-09-30.md.

Endpoint Techo (2 GB) ≈ por GB Cuello Datos movidos
detail ~100 ~50 app (2 workers) 1 hex (~0,7 KB)
area ~100 ~50 app 20–300 hexes (~0,06–0,22 MB)
variables ~100 ~50 app 62 filas meta
warmup >100 >50 — conteo estimado
variables-bulk ~10 ~5 BD (scan bbox) hasta ~165 MB leídos

Regla: ~1 worker ≈ 18 operaciones de BD concurrentes por cada ~1 GB de RAM. variables-bulk es el más caro → el front acota bbox + resolución, cachea de forma acumulativa (ocultar una capa no re-pide) y aborta peticiones en vuelo al cambiar de capas/salir (evita apilamiento que satura el back).

  • Migraciones: Alembic (migrations/versions/). En dev init_db crea tablas; en prod alembic upgrade head. Última: 0015_hexagon_excluded_index (índice parcial para /tiles/excluded).
  • Rendimiento Fase 1 (hecho): warmup con estimado reltuples; caché en proceso de excluidos (EXCLUDED_CACHE_TTL); índice parcial.
  • Fase 2 (propuesta de rediseño h3-pg): extensión H3 de Postgres con PK h3index (BIGINT), partir el JSONB fuera del camino caliente, columnas padre H3 y vistas materializadas por resolución para variables-bulk. Objetivo: subir el cache-hit (hoy ~74 %) y el techo de concurrencia.

9. Seguridad

  • OIDC/Keycloak: login en el front (Auth.js); el backend verifica el JWT contra el JWKS (KEYCLOAK_JWKS_URL), audiencia (KEYCLOAK_AUDIENCE) y algoritmos (JWT_ALGORITHMS).
  • BFF privado: el backend no es público; solo acepta al front vía INTERNAL_API_SECRET (+ identidad reenviada). CORS restringido con CORS_ORIGINS.
  • Roles: endpoints de datos exigen usuario autenticado; /admin/* exige admin.
  • Datos: backend = real o vacío (nunca placeholder). Credenciales fuera del repo (gestor de secretos).

Manual de Instalación — Vento

Puesta en marcha de frontend, backend, base de datos e identidad, con el detalle completo de las variables de entorno y de la ingesta de datos. Usa placeholders (HOST, USUARIO, CLAVE, TU_DOMINIO, secretos) — reemplázalos por los reales del gestor de secretos; no pongas credenciales en el repo. Fecha: 2026-10-01 · Autor: Mavalan Software

0. Prerrequisitos

Componente Requisito
Frontend Node.js (versión indicada por AccuWeb) + npm
Backend Python 3.12 (o Docker)
Base de datos PostgreSQL 14+
Identidad Keycloak (realm con roles admin y analista)
Datos Parquet maestro (data/master_variables.h3.parquet) + InfoVariables.xlsx

Orden recomendado: BD → Keycloak → Backend (+ ingesta) → Frontend.

1. Base de datos (PostgreSQL)

createdb NOMBRE_BD
# o: psql -c "CREATE DATABASE NOMBRE_BD;
#            CREATE USER USUARIO WITH PASSWORD 'CLAVE';
#            GRANT ALL PRIVILEGES ON DATABASE NOMBRE_BD TO USUARIO;"
  • DSN (formato del backend): postgresql+psycopg://USUARIO:CLAVE@HOST_BD:5432/NOMBRE_BD
  • max_connections ≥ (DB_POOL_SIZE + DB_MAX_OVERFLOW) × workers → con 2 workers = 40.
  • Tuning (server chico): shared_buffers ≈ 25 % RAM, work_mem suficiente para los bbox.

2. Identidad (Keycloak)

  1. Crear realm (p.ej. vento) con roles admin y analista.
  2. Crear cliente OIDC para el front (p.ej. vento-web): confidential, con los redirect URIs del dominio del front y el client secret.
  3. El backend solo verifica el JWT (no emite): necesita el issuer, el JWKS y la audiencia.
  4. Asignar el rol admin a quien administre (desde Keycloak o desde Vento → Gestión de usuarios).

3. Backend (FastAPI)

3.1 .env del backend (completo)

# ── Base de datos (requerido) ──
DATABASE_URL=postgresql+psycopg://USUARIO:CLAVE@HOST_BD:5432/NOMBRE_BD

# ── Datos ──
PARQUET_PATH=/app/data/master_variables.h3.parquet   # ruta del parquet maestro
HEXAGON_INGEST=copy                                   # copy (Postgres COPY, rápido) | orm (portable)
INGEST_MEM_CAP_MB=                                    # (opcional) tope de RAM del proceso de ingesta
OFFSHORE_VAR=                                         # código de la columna mar(1)/tierra(0); vacío = no se expone aún

# ── Autenticación (Keycloak — el backend VERIFICA, no emite) ──
KEYCLOAK_ISSUER=https://KEYCLOAK_HOST/realms/vento
KEYCLOAK_JWKS_URL=https://KEYCLOAK_HOST/realms/vento/protocol/openid-connect/certs  # default: {ISSUER}/protocol/openid-connect/certs
KEYCLOAK_AUDIENCE=account
JWT_ALGORITHMS=RS256

# ── BFF (secreto compartido Next → FastAPI) ──
INTERNAL_API_SECRET=<secreto-largo-aleatorio>         # mismo valor en el front; vacío = modo interno off

# ── CORS ──
CORS_ORIGINS=https://TU_DOMINIO                        # coma-separado; default http://localhost:3000

# ── Histórico ──
MAX_HISTORIAL_PER_USER=50

# ── Pool de BD (por worker) ──
DB_POOL_SIZE=5
DB_MAX_OVERFLOW=15        # 5+15 = 20 conexiones/worker (× workers ≤ max_connections)
DB_POOL_TIMEOUT=30        # s esperando una conexión
DB_POOL_RECYCLE=1800      # recicla conexiones viejas (s)

# ── Concurrencia / caché ──
APP_THREAD_LIMIT=18       # threads anyio por worker (consultas BD concurrentes)
EXCLUDED_CACHE_TTL=300    # TTL (s) de la caché de /tiles/excluded

# ── Observabilidad (diagnóstico; dejar off en prod salvo incidente) ──
DEBUG_INFLIGHT=           # =1 activa /api/_debug/stats e /inflight
TRACE_REQUESTS=0          # =1 loguea cada request (entra/sale + duración)
INFLIGHT_WARN=12          # WARNING si ≥N peticiones en vuelo a la vez (apilamiento)
SLOW_REQUEST_MS=3000      # loguea las que tarden más de N ms

En dev el backend carga .env automáticamente (python-dotenv). En prod las variables vienen del entorno/contenedor (no se usa .env).

3.2 Arranque — Docker (producción)

cd backend/AppVento---Backend
docker build -t vento-backend .
docker run -d --name vento-backend -p 8000:8000 --env-file .env vento-backend

El docker-entrypoint.sh aplica migraciones (alembic upgrade head), opcionalmente ingiere el parquet, y arranca gunicorn main:app -k uvicorn.workers.UvicornWorker -w 2 -b 0.0.0.0:8000 --timeout 120.

3.4 Ingesta de datos (detallada)

La ingesta es destructiva por dataset (reemplaza todo) y, en la máster, atómica (TRUNCATE+COPY en una transacción).

  1. Máster (hexágonos): coloca el parquet en PARQUET_PATH e ingiere desde Admin → Subir master (drag-and-drop) o el tool. HEXAGON_INGEST=copy usa COPY (rápido, streaming); orm es el fallback portable. En la misma transacción se recalcula hexagon_meta (min/max por variable).
  2. Catálogo (InfoVariables.xlsx): Admin → Metadatos → catalog_variable (label, dimensión, criterio, fuente, licencia, método, icon_key, enMapa, pesos)
  3. parquet_column.
  4. Normas (regulatoria) y escenarios (económica): Admin → Normativa / Escenarios.
  5. Después de ingerir: VACUUM ANALYZE hexagon; y verifica con GET /api/admin/db/overview (columnas por tabla + diff h3 ↔ catálogo ↔ máster).

4. Frontend (Next.js)

4.1 .env / .env.local del frontend (completo)

# ── Modo ──
NEXT_PUBLIC_USE_BACKEND=true          # true = API real | false = template/demo (sin backend)
NEXT_PUBLIC_API_URL=https://TU_DOMINIO # URL pública de la API (cliente)

# ── BFF (servidor Next → backend) ──
BACKEND_URL=http://HOST_BACKEND:8000   # destino interno del proxy /api/*
INTERNAL_API_SECRET=<secreto-largo-aleatorio>  # mismo valor que en el backend

# ── Auth.js (NextAuth v5) ──
AUTH_SECRET=<secreto-largo-aleatorio>  # firma de la sesión (openssl rand -base64 32)
AUTH_URL=https://TU_DOMINIO            # URL pública del front
AUTH_TRUST_HOST=true

# ── Cliente OIDC (Keycloak) ──
AUTH_KEYCLOAK_ID=vento-web             # client id
AUTH_KEYCLOAK_SECRET=<client-secret>   # client secret del cliente OIDC
AUTH_KEYCLOAK_ISSUER=https://KEYCLOAK_HOST/realms/vento

# ── Keycloak visible al cliente (logout, registro) ──
NEXT_PUBLIC_KEYCLOAK_URL=https://KEYCLOAK_HOST
NEXT_PUBLIC_KEYCLOAK_REALM=vento
NEXT_PUBLIC_KEYCLOAK_ISSUER=https://KEYCLOAK_HOST/realms/vento

# ── Correo (notificaciones, p.ej. al otorgar admin) ──
SENDGRID_API_KEY=<api-key>
SENDGRID_FROM_EMAIL=no-reply@TU_DOMINIO

NEXT_PUBLIC_* se exponen al navegador (no poner secretos ahí). AUTH_*, BACKEND_URL, INTERNAL_API_SECRET, SENDGRID_* son solo de servidor. INTERNAL_API_SECRET debe ser idéntico en front y backend.

7. Red de seguridad de memoria (server chico)

# Swap 4 GB persistente
sudo fallocate -l 4G /swapfile || sudo dd if=/dev/zero of=/swapfile bs=1M count=4096
sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
sudo sysctl -w vm.swappiness=10
echo 'vm.swappiness=10' | sudo tee /etc/sysctl.d/99-swappiness.conf
# earlyoom (mata el proceso correcto antes del OOM del kernel)
sudo apt-get update && sudo apt-get install -y earlyoom
sudo systemctl enable --now earlyoom

Mitigaciones, no la solución: el fix real de capacidad es el rediseño de datos (Fase 2) + más RAM/workers.
