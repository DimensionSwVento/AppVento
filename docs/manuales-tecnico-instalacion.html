Manual Técnico — Vento (Plataforma de idoneidad eólica)

Arquitectura, comportamiento, datos, seguridad, configuración y operación. Escrito a partir de una lectura completa del código (front + backend). Audiencia: equipo de desarrollo / on-call. No es el manual de usuario. Fecha: 2026-10-01 · Autor: Mavalan Software

1. Qué es Vento

Plataforma SIG/MCDM que evalúa la idoneidad de zonas para proyectos eólicos en Colombia sobre una malla de hexágonos H3 (resolución 8). El usuario selecciona un área, el sistema agrega un índice de idoneidad (0–100) por dimensión y general, y genera un informe PDF configurable. El admin gestiona variables, datasets, normas, escenarios económicos y usuarios.

  • Modelo (clave): todo va en escala 1–5 (−1 = excluida). La normalización a [0,1] se hace en LECTURA ((raw−1)/4), nunca en ingesta. El global y los scores vienen precalculados en la máster; la app agrega/formatea, no recalcula el modelo.
  • Dimensiones: Técnica, Ambiental, Social (puntuables) + Económica y Regulatoria (informativas, no puntúan).

2. Arquitectura

Navegador ──HTTPS──▶ Front Next.js 16 (App Router)  ── BFF: rutas /api/* ──▶ Backend FastAPI (Docker)
   Auth.js (NextAuth v5)      │  backendProxy.ts: await auth() → exige sesión;             │  gunicorn -w 2
   cookie __Secure-authjs…    │  añade X-Internal-Secret + X-User-Sub + X-User-Roles       │  (stateless)
                              │  (NO relaya access tokens)                                 ▼
                              │                                                        PostgreSQL
                              └── Keycloak (OIDC) ◀── el backend VERIFICA el JWT (JWKS)   (hexagon 1.6M, catalog_*, …)
  • BFF (Backend-for-Frontend): el navegador no habla con el backend. Las rutas /api/* del front (Utils/apis/backendProxy.ts) validan la sesión de Keycloak y reenvían al backend privado (BACKEND_URL) con X-Internal-Secret (= INTERNAL_API_SECRET) + identidad (X-User-Sub, X-User-Roles). cache: no-store; 502 si el backend no responde. Nunca se mandan access tokens al cliente (cookie <4KB).
  • Backend stateless: nada se carga a RAM al arrancar; cada request consulta Postgres en streaming (anti-OOM). Clean architecture: api/ (routers) · application/ (servicios) · domain/ (motor de consulta/modelo) · infrastructure/ (BD, auth, datos).
  • Identidad: Keycloak como IdP (OIDC). El front usa Auth.js (NextAuth v5, provider Keycloak custom); el backend solo verifica el JWT (no emite).

Flag (derivado) Efecto

6. Mapa (deck.gl)

Map.tsx usa react-map-gl/maplibre (basemap CartoDB) + DeckGL. Capas principales: - gridTileLayer (TileLayer): calcula celdas H3 del bbox del tile a la resolución del zoom (zoomToH3Res) y filtra "solo lo visible" dentro de Colombia (ADR-014). Pinta viento (viridis) o gris (excluidas). Visible/pickable solo fuera del heatmap del informe. - informeHeatmapLayer (useInformeHeatmapLayer): malla res-8 del área con color por backendScore real (o placeholder/transparente según modo); se normaliza cualquier res a 8. - selección / bordes / hover / símbolos (zona, punto, iconos) / dibujo de polígono. - Capas de variable: se piden por bbox (/api/tiles/variable[s-bulk]), con caché y cancelación de las peticiones en vuelo al cambiar de capas o salir (evita apilar scans que saturan el backend). Ocultar una capa no vuelve a pedir datos. - Excluidas: se cargan como capa completa en una sola petición (/tiles/excluded) y se marcan con isHexBanned (sin pedir tile-por-tile). El emplazamiento (mar/tierra) y la exclusión por dato se alimentan desde /tiles/area (setBannedData/setEsOffshoreData).

7. Informe / PDF

Report.tsx arma "hojas" A4 (794×1123 @96dpi, ReportSheet) según la configuración: índice + resumen ejecutivo (índice Gauge, gráfico por dimensión, top-influencers DivergingBars, snapshot del mapa) · una hoja por dimensión puntuable (score, peso, tabla paginada, excluyentes, resumen del cálculo) · económica (LineChart) · regulatoria (semáforo + normas + autoridades) · informativas · fuentes · disclaimer. Los gráficos son SVG puro (sin librería) para capturarse limpios.

Pipeline de exportación PDF: 1. Escala las hojas a 1 y espera a que rendericen (rAF + delay). 2. Recorre cada [data-report-sheet] — una hoja = una página A4. 3. html2canvas-pro(sheet, {scale: 2, jpeg 0.95}) → jsPDF.addImage (ajuste "contain" a A4). 4. Chunking: las tablas largas (variables consideradas, intervalos de ponderación, normas, fuentes) se parten en varias hojas para que nunca se corten a mitad; el resto de secciones también respeta el A4. 5. pdf.save(...). El snapshot del mapa se compone de los <canvas> (basemap + deck) y se cachea; el informe lo lee como <img>.

8. Ingesta de datos (comportamiento)

La normalización 1–5→[0,1] se hace en LECTURA; la ingesta guarda el dato crudo. Hay cuatro caminos (según el caso) + los ingestores de catálogo:

Camino Dónde Comportamiento
copy (default máster) hexagon_repository.copy_ingest COPY de Postgres, atómico (TRUNCATE+COPY+hexagon_meta en una transacción), streaming dict→tupla→COPY. Máximo rendimiento.
orm (portable) replace_all DELETE + lotes de 5000 vía ORM (sin COPY). No atómico (ventana con tabla parcial). Fallback para tests.
upsert_chunk (modular) upsert_chunk ingesta por paquete/row-group: ON CONFLICT fusiona JSONB (variables/scores con ||), refina hexagon_meta con least/greatest. No vacía la tabla.
blue_green (prod segura) blue_green_replace carga en hexagon_new y hace SWAP atómico por rename; la app lee hexagon durante toda la carga (sin downtime).
  • Bundle por clases (bundle_service): subir máster drag-and-drop → plan (lee solo el footer, clasifica columnas contra parquet_column) → apply protegido por advisory lock pg_try_advisory_lock (single-flight anti-OOM), merge outer por h3_index de a un parquet con malloc_trim (libera RSS), ruteo por clase (global→score_general, criterio/subcriterio→scores, variable_*/alerta→variables, excluyente→tipo_celda). El camino más pesado corre aislado en subproceso (apply_detached con RLIMIT_AS = INGEST_MEM_CAP_MB).
  • Catálogo (metadata_ingest): InfoVariables.xlsx → jerarquía dimension→criterio→ subcriterio→variable, concilia cada variable por master_id, rutea filas REG… a catalog_norma. Económico (economic_ingest): bundle macro → tabla long economic_series + economic_panel.
  • Después de ingerir: VACUUM ANALYZE hexagon; (para reltuples/visibility map) y verificar con GET /api/admin/db/overview (columnas por tabla + diff h3 ↔ catálogo ↔ máster).

11. Seguridad y autenticación

  • Front (Auth.js / NextAuth v5): provider Keycloak custom (reescritura de issuer para AccuWeb). El jwt callback persiste roles (de realm_access.roles) y refresca el token; el session expone solo roles/sub/error (no tokens). SessionGuard cierra sesión si falla el refresh.
  • Guard de admin triple: middleware.ts (redirect) + admin/layout.tsx (server) + rutas BFF admin (403 si no admin). useIsAdmin() es solo UI.
  • Registro (ADR-012): /api/auth/register → Keycloak /registrations con state CSRF; el callback hace token-exchange + logout federado y nunca crea sesión NextAuth. kc-logout = logout federado. Gestión de usuarios usa la Keycloak Admin API (no FastAPI); "eliminar" = deshabilitar (soft). Notificación de promoción a admin vía SendGrid.
  • Backend (keycloak_guard): require_user es dual — (a) modo BFF: si X-Internal-Secret coincide con INTERNAL_API_SECRET, toma identidad de X-User-* sin validar JWT; (b) si no, valida el Bearer JWT contra el JWKS (firma RS256 + issuer; verify_aud=False). require_admin exige rol. CORS restringido con CORS_ORIGINS.
  • Datos: backend = real o vacío. Credenciales fuera del repo.

12. Capacidad (medida con tools/loadtest.py)

Server 2 workers / ~2 GB. Techo útil ≈ 25 usuarios concurrentes explorando (evidencia: docs/testing/benchmark-carga-h3-2026-09-30.md).

Endpoint Techo (2 GB) ≈ por GB Cuello Datos movidos
detail / area / variables ~100 ~50 app (2 workers) 1 hex / 20–300 hexes / meta
warmup >100 >50 — conteo estimado
variables-bulk ~10 ~5 BD (scan bbox) hasta ~165 MB leídos

Regla: 2 workers × APP_THREAD_LIMIT(18) = 36 operaciones de BD concurrentes (de ahí el techo). Más capacidad = más workers (necesita RAM) o escalar; respetar APP_THREAD_LIMIT ≤ DB_POOL_SIZE+DB_MAX_OVERFLOW y (pool)×workers ≤ max_connections.

Manual de Instalación — Vento

Puesta en marcha de frontend, backend, base de datos e identidad, con el detalle completo de las variables de entorno y de la ingesta de datos. Usa placeholders (HOST, USUARIO, CLAVE, TU_DOMINIO, secretos) — reemplázalos por los reales del gestor de secretos; no pongas credenciales en el repo. Fecha: 2026-10-01 · Autor: Mavalan Software

0. Prerrequisitos

Componente Requisito
Frontend Node.js (versión indicada por AccuWeb) + npm
Backend Python 3.12 (o Docker)
Base de datos PostgreSQL 14+
Identidad Keycloak (realm con roles admin y analista)
Datos Parquet maestro (data/master_variables.h3.parquet) + InfoVariables.xlsx

Orden recomendado: BD → Keycloak → Backend (+ ingesta) → Frontend.

Opción rápida — docker-compose (dev, todo en uno)

El backend trae un docker-compose.yml que levanta Postgres + Keycloak + backend:

cd backend/AppVento---Backend
docker compose up -d        # db (postgres:16), keycloak (26.1, importa deploy/keycloak/), app (:8000)
# el realm se importa desde deploy/keycloak/vento-realm.json; la BD queda en el volumen pgdata

Para producción, sigue las secciones 1–8 (servicios separados). Artefactos de despliegue: deploy/vento-backend.service (systemd), deploy/keycloak/ (realm), DEPLOY.md.

1. Base de datos (PostgreSQL)

createdb NOMBRE_BD
# o: psql -c "CREATE DATABASE NOMBRE_BD;
#            CREATE USER USUARIO WITH PASSWORD 'CLAVE';
#            GRANT ALL PRIVILEGES ON DATABASE NOMBRE_BD TO USUARIO;"
  • DSN (formato del backend): postgresql+psycopg://USUARIO:CLAVE@HOST_BD:5432/NOMBRE_BD
  • max_connections ≥ (DB_POOL_SIZE + DB_MAX_OVERFLOW) × workers → con 2 workers = 40.
  • Tuning (server chico): shared_buffers ≈ 25 % RAM, work_mem suficiente para los bbox.

2. Identidad (Keycloak)

  1. Crear realm (p.ej. vento) con roles admin y analista.
  2. Crear cliente OIDC para el front (p.ej. vento-web): confidential, con los redirect URIs del dominio del front y el client secret.
  3. El backend solo verifica el JWT (no emite): necesita el issuer, el JWKS y la audiencia.
  4. Asignar el rol admin a quien administre (desde Keycloak o desde Vento → Gestión de usuarios).

3. Backend (FastAPI)

3.1 .env del backend (completo)

# ── Base de datos (requerido) ──
DATABASE_URL=postgresql+psycopg://USUARIO:CLAVE@HOST_BD:5432/NOMBRE_BD

# ── Datos ──
PARQUET_PATH=/app/data/master_variables.h3.parquet   # ruta del parquet maestro

OFFSHORE_VAR=                                         # código de la columna mar(1)/tierra(0); vacío = no se expone aún

# ── Autenticación (Keycloak — el backend VERIFICA, no emite) ──
KEYCLOAK_ISSUER=https://KEYCLOAK_HOST/realms/vento
KEYCLOAK_JWKS_URL=https://KEYCLOAK_HOST/realms/vento/protocol/openid-connect/certs  # default: {ISSUER}/protocol/openid-connect/certs
KEYCLOAK_AUDIENCE=account
JWT_ALGORITHMS=RS256

# ── BFF (secreto compartido Next → FastAPI) ──
INTERNAL_API_SECRET=<secreto-largo-aleatorio>         # mismo valor en el front; vacío = modo interno off

# ── CORS ──
CORS_ORIGINS=https://TU_DOMINIO                        # coma-separado; default http://localhost:3000

# ── Histórico ──
MAX_HISTORIAL_PER_USER=50

# ── Pool de BD (por worker) ──
DB_POOL_SIZE=5
DB_MAX_OVERFLOW=15        # 5+15 = 20 conexiones/worker (× workers ≤ max_connections)
DB_POOL_TIMEOUT=30        # s esperando una conexión
DB_POOL_RECYCLE=1800      # recicla conexiones viejas (s)

# ── Concurrencia / caché ──
APP_THREAD_LIMIT=18       # threads anyio por worker (consultas BD concurrentes)
EXCLUDED_CACHE_TTL=300    # TTL (s) de la caché de /tiles/excluded

# ── Ingesta al arrancar (entrypoint) ──
RUN_INGEST=              # =true → el docker-entrypoint.sh ejecuta tools.ingest_parquet (ingesta destructiva) antes de gunicorn

# ── Observabilidad (diagnóstico; dejar off en prod salvo incidente) ──
DEBUG_INFLIGHT=           # =1 activa /api/_debug/stats e /inflight
TRACE_REQUESTS=0          # =1 loguea cada request (entra/sale + duración)
INFLIGHT_WARN=12          # WARNING si ≥N peticiones en vuelo a la vez (apilamiento)
SLOW_REQUEST_MS=3000      # loguea las que tarden más de N ms

En dev el backend carga .env automáticamente (python-dotenv). En prod las variables vienen del entorno/contenedor (no se usa .env).

3.4 Ingesta de datos (detallada)

La ingesta es destructiva por dataset (reemplaza todo) y, en la máster, atómica (TRUNCATE+COPY en una transacción).

  1. Máster (hexágonos): coloca el parquet en PARQUET_PATH e ingiere desde Admin → Subir master (drag-and-drop) o el tool. HEXAGON_INGEST=copy usa COPY (rápido, streaming); orm es el fallback portable. En la misma transacción se recalcula hexagon_meta (min/max por variable).
  2. Catálogo (InfoVariables.xlsx): Admin → Metadatos → catalog_variable (label, dimensión, criterio, fuente, licencia, método, icon_key, enMapa, pesos)
  3. parquet_column.
  4. Normas (regulatoria) y escenarios (económica): Admin → Normativa / Escenarios.
  5. Después de ingerir: VACUUM ANALYZE hexagon; y verifica con GET /api/admin/db/overview (columnas por tabla + diff h3 ↔ catálogo ↔ máster).

NEXT_PUBLIC_API_URL=https://TU_DOMINIO # URL pública de la API (cliente)

# ── BFF (servidor Next → backend) ──
BACKEND_URL=http://HOST_BACKEND:8000   # destino interno del proxy /api/*
INTERNAL_API_SECRET=<secreto-largo-aleatorio>  # mismo valor que en el backend

# ── Auth.js (NextAuth v5) ──
AUTH_SECRET=<secreto-largo-aleatorio>  # firma de la sesión (openssl rand -base64 32)
AUTH_URL=https://TU_DOMINIO            # URL pública del front
AUTH_TRUST_HOST=true

# ── Cliente OIDC (Keycloak) ──
AUTH_KEYCLOAK_ID=vento-web             # client id
AUTH_KEYCLOAK_SECRET=<client-secret>   # client secret del cliente OIDC
AUTH_KEYCLOAK_ISSUER=https://KEYCLOAK_HOST/realms/vento

# ── Keycloak visible al cliente (logout, registro) ──
NEXT_PUBLIC_KEYCLOAK_URL=https://KEYCLOAK_HOST
NEXT_PUBLIC_KEYCLOAK_REALM=vento
NEXT_PUBLIC_KEYCLOAK_ISSUER=https://KEYCLOAK_HOST/realms/vento

# ── Correo (notificaciones, p.ej. al otorgar admin) ──
SENDGRID_API_KEY=<api-key>
SENDGRID_FROM_EMAIL=no-reply@TU_DOMINIO

NEXT_PUBLIC_* se exponen al navegador (no poner secretos ahí). AUTH_*, BACKEND_URL, INTERNAL_API_SECRET, SENDGRID_* son solo de servidor. INTERNAL_API_SECRET debe ser idéntico en front y backend.

7. Red de seguridad de memoria (server chico)

# Swap 4 GB persistente
sudo fallocate -l 4G /swapfile || sudo dd if=/dev/zero of=/swapfile bs=1M count=4096
sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
sudo sysctl -w vm.swappiness=10
echo 'vm.swappiness=10' | sudo tee /etc/sysctl.d/99-swappiness.conf
# earlyoom (mata el proceso correcto antes del OOM del kernel)
sudo apt-get update && sudo apt-get install -y earlyoom
sudo systemctl enable --now earlyoom

Mitigaciones, no la solución: el fix real de capacidad es el rediseño de datos (Fase 2) + más RAM/workers.
